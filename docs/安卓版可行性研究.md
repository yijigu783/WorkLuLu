# 工作记录本 WorkLuLu · 安卓版可行性研究

> 研究日期：2026-09-27
> 研究范围：现有 Windows 版（1.2.0）能否移植到安卓，怎么移植，代价在哪
> 结论状态：**技术可行，但「1:1 移植」不成立**。三条路线见第五节

---

## 一、结论摘要

先说三句话：

1. **Rust 业务逻辑几乎可以整份复用**——`schedule.rs` 一行都不用改。这部分是意外之喜。
2. **界面不能复用，必须重做**——不是"调一下宽度"，是交互范式整个换掉。现有前端对触屏的适配量是**零**。
3. **最大的坑不是界面，是后台提醒**。桌面版那套"每 30 秒轮询一次"的做法，在安卓上**一行都用不了**，而提醒恰恰是这个软件的核心价值。

另外有一个**开工前必须确认的前提**（见第七节），它可能直接决定这件事做不做得成。

---

## 二、现有资产盘点

### 2.1 代码规模与可移植性

| 文件 | 行数 | 平台耦合 | 可移植性 |
|---|---|---|---|
| `schedule.rs` | 494 | **0 处** `tauri::` | **100% 直接复用**，纯日期逻辑，连测试都能搬 |
| `db.rs` | 193 | 3 处 | 约 95%，只有 `data_dir()` 用了 Tauri 的路径 API |
| `commands.rs` | 1978 | 36 处 | 大部分复用，**29 个 command 是核心资产** |
| `notify.rs` | 102 | **全 Windows** | **0%**，`#![cfg(windows)]` + Win32 注册表 + winrt，得整个重写 |
| `main.rs` | 548 | 13 处 | 需大改：托盘、窗口事件在这一层 |
| 前端 `app.js` | 2970 | — | 数据/渲染逻辑复用，**交互层重做** |
| 前端 `style.css` | 804 | — | **基本重写**（见 3.2） |
| `index.html` | 61 | — | 复用 |

**总计约 7150 行**，其中约 **2500 行（35%）可以基本原样搬过去**。

### 2.2 一个有利的结构事实

Windows 专有代码**没有渗透进业务层**：

- `notify.rs` 整个文件被 `#![cfg(windows)]` 关在一个文件里，对外只暴露两个函数（`ensure_app_id` / `show_task_toast`）。
- `Cargo.toml` 已经把 `windows` crate 和 `tauri-winrt-notification` 放在 `[target.'cfg(windows)'.dependencies]` 下单独门控。
- `schedule.rs` 是一个 tauri 都不依赖的纯函数库。

这意味着**平台移植的切口已经在正确的位置上了**，不是那种"到处都撒着 `#[cfg(windows)]`"的乱局。这是当初分层做得好的回报。

## 三、三类移植障碍

### 3.1 架构障碍：缺 `lib.rs`（必改，但改起来清楚）

Tauri 移动端的入口**只在 `lib.rs`**：

```rust
#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() { /* ... */ }
```

官方文档的原话是：**"Nothing you write in `main.rs` runs on mobile."**

本项目目前只有 `main.rs`，没有 `lib.rs`。所以：

- 必须把 `Builder` 链、`setup`、`invoke_handler` 全部搬进 `lib.rs` 的 `run()`；
- `main.rs` 退化成一行 `fn main() { app_lib::run() }`；
- 托盘那一段用 `#[cfg(desktop)]` 包起来——安卓上**没有系统托盘**，也没有等价物。

顺便，`main.rs` 里这几样在安卓上都不成立，需要平台分支：

| 现有实现 | 安卓上的情况 |
|---|---|
| `TrayIconBuilder` + 右键菜单 | **不存在**，整个砍掉 |
| `CloseRequested` → 收进托盘 | 手机没有"关闭窗口"这个概念 |
| `tauri-plugin-autostart` | **Android ✗**（官方支持矩阵里明确标不支持） |
| `tauri-plugin-dialog`（另存为/打开） | 支持，但语义变成 SAF 文档选择器，备份/恢复的流程要重设计 |
| `data_dir()` → `%APPDATA%\工作记录本` | 变成应用私有沙箱目录，**用户看不到也进不去**，"打开数据目录"这个功能失去意义 |

### 3.2 交互障碍：桌面范式 vs 触屏（这块最被低估）

我逐行数了 `style.css` 和 `app.js`：

| 指标 | 数量 | 后果 |
|---|---|---|
| `:hover` 规则 | **34 处** | 触屏没有 hover（首次点击只触发 hover 态，不触发 click） |
| `@media` 媒体查询 | **0 处** | **完全没有响应式设计**，一个断点都没有 |
| 触屏事件兜底（`touchstart`/`pointerdown`/`touch-action`） | **0 处** | 零适配 |
| 窗口配置 | 1120×720，`minWidth: 900` | 手机可用宽度约 **360–420dp**，差了 2.5 倍 |

**这不只是"样式不好看"，有三处是功能性缺陷：**

1. `style.css:545` — `.nav-item:hover .nav-edit { display: flex; }`
   分类的**编辑按钮只在 hover 时显形**。手机上这个按钮**永远显示不出来**，用户无法重命名分类。而这一条**没有 focus 兜底**。
2. `style.css:330` — `.task:hover .task-actions .icon-btn`
   任务的**操作按钮（编辑/删除等）同样靠 hover 显形**。
3. `style.css:589 / 593` — 子任务的删除、加子级按钮。这两处写了 `:focus-visible` 兜底，但触屏上 `focus-visible` 的触发同样不可靠。

**还有四个交互在手机上直接失效：**

| 桌面交互 | 位置 | 手机上的问题 |
|---|---|---|
| HTML5 拖拽排序分类 | `app.js:2497` `dragstart` / `dragover` / `drop` | **HTML5 DnD 在触屏上不触发**，得改成 `pointerdown` 长按拖拽或上下箭头按钮 |
| 滚轮翻月 | `app.js:2850` `wheel` | 触屏无滚轮。可改成左右滑动，但 250ms 节流逻辑要重写 |
| 右键上下文菜单 | `app.js:2876` `contextmenu` | 长按可触发，但要处理与系统长按菜单的冲突 |
| `Ctrl+N` 新建 | `app.js:2843` `keydown` | 手机没有键盘，得给个常驻的「＋」悬浮按钮 |

另外 **日历视图（7 列 grid）和看板视图**在 360dp 宽度下基本没法用——7 列每列不到 50dp。手机端合理的形态是**单列列表 + 底部 Tab**，日历要重新设计成"月历点选 + 当日列表"两层。

### 3.3 提醒障碍：安卓上最硬的一块（核心风险）

这是整个移植里**技术风险最高、最不可控**的部分。

**桌面版现在的做法**（`main.rs:266`）：

```rust
fn spawn_reminder_loop(app) {
    std::thread::spawn(move || loop {
        std::thread::sleep(TICK);   // TICK = 30 秒
        tick(&app);                 // 补排期 → 捞到期的 → 弹通知
    });
}
```

配套的三件事在 Windows 上都成立：进程常驻（关窗收托盘）、每 30 秒准点醒、`notify.rs` 弹 winrt toast。

**安卓上这三件事全部不成立：**

- **进程不常驻**。用户切走、锁屏、系统回收，进程就没了。`sleep(30s)` 的线程随进程一起消失。
- **系统会主动冻结后台**。Doze 模式、App Standby 桶、厂商省电策略，都会延迟甚至丢弃你的定时任务。
- **准点弹通知要专门申请权限**，而且用户可能拒绝。

**安卓上正确的做法**（需要写 Kotlin 侧代码，Tauri 插件机制）：

| 方案 | 精度 | 前置条件 |
|---|---|---|
| `WorkManager` 周期任务 | **不精确**，最小间隔 15 分钟 | 无需特殊权限，但"9:30 的晨会"可能 9:45 才响 |
| `AlarmManager.setExactAndAllowWhileIdle` | 精确 | 需要 `SCHEDULE_EXACT_ALARM`；**Android 14+ 必须引导用户去系统设置手动开启** |
| `setAlarmClock()` | 最高 | 会在状态栏显示闹钟图标，用户可见 |

**三个必须处理的权限（缺一个就静默失效）：**

- `POST_NOTIFICATIONS` —— Android 13+ 运行时权限。没有它，通知**根本不显示**。
- `SCHEDULE_EXACT_ALARM` —— Android 12+。14+ 起需要用户去系统设置里手动开。
- `RECEIVE_BOOT_COMPLETED` —— **最常被忘记的一个**。没有它，手机重启后所有定时任务**全部消失**，且不会报错。必须在 `BOOT_COMPLETED` 广播里重新注册。

**以及国产 ROM 这个现实：**

| 厂商 | 省电策略 | 表现 |
|---|---|---|
| 小米 | 神隐模式 | 限制 Alarm 唤醒、默认禁自启 |
| 华为 | 智能省电 / 应用启动管理 | 默认关闭自启动和后台活动 |
| OPPO | 高压保护 | 杀后台、限制后台网络 |
| vivo | 后台高耗电管控 | 定时任务延迟或丢弃 |

**结论：即使代码完全写对，也做不到桌面版那种"准点必响"。** 需要引导用户手动加白名单（关电池优化 + 允许自启动 + 锁定后台），而这类引导在界面上很劝退。

**另外，`notify.rs` 的"点通知跳回那一条工作"这个体验在安卓上要重新实现。** 桌面版靠 winrt 的 `on_activated` 回调 + `notify://open-task` 事件（`notify.rs:101`）。安卓侧要用 `PendingIntent` + `Intent` extra，再由 Kotlin 侧转发给 Tauri。这是可行的，但属于"另一套实现"，不是改改就行。

### 3.4 其他要注意的

- **WebView 版本**：安卓用的是**系统 WebView**（不是打包进去的），国内设备版本碎片化严重。前端用了 CSS 变量、Grid、可选链、模板字符串等，需要 Chrome 80+ 内核。现代设备没问题，老设备/鸿蒙兼容层要实测。
- **APK 体积**（估算）：桌面 exe 4.27 MB。安卓版 Rust 编译出的 `.so` 要按 ABI 分别产出，只出 `arm64-v8a` 约 8–10 MB；若同时出一代 armv7 + x86_64 给模拟器，会到 15–20 MB。**比桌面版大是正常的**。
- **`decorations: false`**：现在是自绘标题栏（`.win-btn` / `.win-close`）。手机上不需要，应该改回系统状态栏，这一段 CSS 可以整块删掉。

## 四、开发环境现状：本机从零开始

我查了这台机器的实际情况：

| 项 | 现状 |
|---|---|
| JDK | **未安装**（`JAVA_HOME` 为空，`java` 命令不存在）· 需要 JDK 17+ |
| Android SDK | **未安装**（`ANDROID_HOME` 未设置，默认路径不存在） |
| Android NDK | **未安装** |
| `adb` | **未安装** |
| Rust 安卓目标 | **一个都没有**（只装了 `x86_64-pc-windows-msvc`）· 需要 4 个 target |
| `cargo-tauri` CLI | **未安装** |
| `.cargo/config.toml` | **不存在**（交叉编译 linker 配置） |
| `gen/android/` | **不存在**（移动工程还没 init） |

**也就是说，第一步不是写代码，是把工具链装起来。** 这是一次几百 MB 到几 GB 的下载，加上 `rustup target add aarch64-linux-android armv7-linux-androideabi i686-linux-android x86_64-linux-android`。

好消息是：**安卓构建在 Windows 上就能做**（不像 iOS 必须在 macOS）。所以这台机器可以直接开工，不需要换环境。

还有一个技术点值得先验证：**`rusqlite` 的 `bundled` 特性在安卓上需要交叉编译 SQLite 的 C 源码**，要用 `cargo-ndk` 处理 linker。社区里有成功案例，但踩过坑（Android 上 `SQLITE_TEMP_STORE=2` 曾导致保存点相关问题）。**建议第一步就先做一个空壳验证，确认 `rusqlite` 能编过再往下走**——这是最容易卡住的地方。

## 五、四条路线对比

| 路线 | 做法 | 复用率 | 提醒能力 | 主要代价 |
|---|---|---|---|---|
| **A. 完整移植** | Tauri 2 Android，功能对齐桌面版 | Rust 逻辑 ~90%，前端交互重做 | 需写 Kotlin 插件 + 权限引导，**仍做不到准点必响** | 工作量最大；提醒可靠性打折；要接受国产 ROM 差异 |
| **B. 轻量伴侣** | 只做「查看 + 勾选 + 快速新建」，**砍掉后台提醒** | 同上，但省掉整个 Kotlin 层 | 不做提醒（或交给系统日历） | 功能比桌面版少一半，但**砍掉了 80% 的风险** |
| **C. 网页 / PWA** | 前端搬到浏览器，数据换 IndexedDB 或 WASM SQLite | 前端 UI 可复用，**Rust 后端全废** | 不可靠（Web Push 要服务器 + HTTPS） | 等于重写数据层，且"本地优先"的卖点丢了 |
| **D. 不做 App** | 保持桌面版，加 CSV 互通；手机上用手头已有的待办 App | — | 用别人的 | 不是产品，是绕路 |

**关于路线 B 的判断依据**：手机端"记录工作"的真实使用场景是**随手看一眼、勾一下、临时加一条**，不是坐在手机上排期。而「看」和「勾」这两件事**完全不需要后台提醒**。砍掉提醒，就砍掉了整个安卓开发里最难、最不可控、最容易被厂商 ROM 搞死的部分，同时保住了桌面版做不了的场景（出门在外、开会时随手记）。

## 六、建议

**如果只做一件事**：先做 **3.3 节的技术验证**——用现有代码起一个空壳，确认 `rusqlite` 能交叉编译到 `aarch64-linux-android`，且能启动。这一步不通，后面都不用谈。半天内能有结论。

**如果决定要做**，建议顺序：

1. 装工具链（Android Studio + SDK + NDK + JDK17 + 4 个 rust target + cargo-ndk）
2. 空壳验证：`rusqlite` 交叉编译 + 启动 + 建库
3. 拆 `lib.rs`，把托盘/自启动用 `#[cfg(desktop)]` 隔离，**保证 Windows 版不回归**（现有 62 个测试必须全绿）
4. 前端另起一套移动版样式（不要改桌面版那 804 行 CSS，直接写 `style.mobile.css`），**优先解决 3.2 节那三处 hover 显形的功能缺陷**
5. 最后再碰提醒——先把"查看 + 勾选"跑通

**关于路线选择，我倾向 B。** 理由在上一节。但如果目标是"手机和电脑功能一致"，那就走 A，并且**提前接受提醒不可靠这个事实**——不要花大力气追求准点，那是安卓生态本身的问题，不是代码能解决的。

## 七、开工前必须确认的前提

### 7.1 目标设备到底是什么系统（**最关键**）

如果目标设备是**纯血鸿蒙（HarmonyOS NEXT）**，那么 **Android APK 根本装不上**，只能通过卓易通这类 Android 兼容容器运行。而容器环境对后台运行、通知、权限的限制**比原生安卓更严**——3.3 节的提醒问题会进一步恶化，甚至可能完全不可行。

**这一条必须在投入开发之前确认。** 如果是鸿蒙，可能需要重新评估（比如只做数据导出，或者考虑鸿蒙原生的 ArkTS 方案，那是完全另一条技术路线）。

### 7.2 要的是什么范围的版本

- 完整功能（含提醒）→ 路线 A，接受提醒打折
- 轻量伴侣（查看 + 勾选）→ 路线 B，风险最低
- 只是想在手机上看一眼 → 可能路线 D 更划算（CSV 导出到现有待办 App）

### 7.3 谁来用

如果只是自己用，怎么做都行。如果要分发给吾爱那批用户，还要考虑：APK 签名、无法上国内应用商店（个人开发者上架难）、无签名 APK 同样会被各家手机管家报毒——**这和桌面版是同一个问题，且手机上的拦截更硬**（安装前直接被拦，用户可能装不上）。
