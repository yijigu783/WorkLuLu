# 工作记录本 · 双版本架构方案（Android / HarmonyOS）

> 研究日期：2026-09-27
> 前提：用户决定**安卓与鸿蒙分开做成两个独立版本**
> 配套文档：`安卓版可行性研究.md`（安卓侧的单独研究）

---

## 一、结论摘要

分开做是对的，因为**这不是同一个平台的两种打包，而是两条独立技术路线**：

| | 安卓版 | 鸿蒙版 |
|---|---|---|
| 技术栈 | Tauri 2（Rust + WebView） | **ArkTS + ArkUI**（或 ArkTS + Web 组件） |
| 语言 | Rust + JS | **ArkTS**（TypeScript 超集） |
| IDE | 任意 + Android Studio | **DevEco Studio**（IntelliJ fork） |
| 构建 | cargo + Gradle | **hvigor**（Node DSL） |
| 产物 | `.apk` | `.hap` |
| 分发 | **自由**（发文件即可） | **受限，见第五节** |

三条最重要的判断：

1. **数据层可以三端统一**——Windows 用 `rusqlite`、鸿蒙用 `RelationalStore`，但**两者底层都是 SQLite**，schema 和 SQL 能共用一份。
2. **前端 UI 也能三端统一**——鸿蒙的 `Web` 组件（ArkWeb）能加载本地 HTML，和 Tauri 的 WebView 是同一个思路。
3. **鸿蒙最大的坎不是技术，是分发**。这是 Windows 版从来不需要面对的问题（见第五节），**建议在动工前先想清楚**。

---

## 二、核心洞察：三端共享什么

这是整个方案的价值所在。如果三个版本各写各的，维护成本会失控。

### 2.1 三端的技术底座其实高度同构

| 层 | Windows | Android | HarmonyOS | 可共享？ |
|---|---|---|---|---|
| **数据库** | `rusqlite`（bundled SQLite） | `rusqlite`（bundled SQLite） | `RelationalStore`（**封装 SQLite**） | ✅ **同一份 schema + SQL** |
| **业务逻辑** | Rust `schedule.rs` | Rust `schedule.rs` | ArkTS 重写 或 ohos-rs | ⚠️ 见 4.3 |
| **UI 渲染** | Tauri WebView | Tauri WebView(系统) | `Web` 组件（ArkWeb） | ✅ **同一份 HTML/CSS/JS** |
| **通知** | winrt toast | Android Notification | HarmonyOS 通知 | ❌ 各写各的 |
| **后台提醒** | `sleep(30s)` 轮询 | WorkManager / 精确闹钟 | 鸿蒙后台任务 | ❌ 各写各的（差异最大） |

**这张表是整个方案的地基**：数据库和 UI 两层可以共享，通知和后台提醒必须各写各的。

### 2.2 一个附带的收获：数据可以互通

三端都是 SQLite → **理论上桌面版的 `worklog.db` 可以直接给手机端打开**。

这对用户是实打实的价值（在电脑上排好期，拷到手机上执行）。要做的话，加一个「导入/导出数据库文件」功能即可——现有 `backup_to` / `restore_from` 已经是 `VACUUM INTO` + `ATTACH` 的实现，**逻辑可以直接照搬到两端**。

⚠️ 但要注意：鸿蒙的应用目录是**沙箱**，用户进不去，必须走系统的文件选择器（和安卓 SAF 一个道理）。所以「打开数据目录」这个功能在两端都要去掉，换成「导出到…」。

### 2.3 最要命的一条纪律：排期算法必须三端一致

`schedule.rs` 那 494 行负责算「下一次什么时候」——每月最后一个工作日、每周三、带节假日跳过……**如果三端各写一遍算法，早晚会出现同一个周期任务在三端算出不同日期的 bug**，而且这种 bug 极难发现（用户不会想到是端的问题）。

所以规则是：**一份算法定义，三端实现必须用同一组测试用例验证**。现有 `cargo test` 里排期相关的用例可以导出成一份 JSON，安卓端直接复用 Rust 测试，鸿蒙端用同一份 JSON 跑 ArkTS 测试。

## 三、建议的目录结构

现有平铺结构（`app/ui` + `app/src-tauri`）在单端时够用，三端会乱。建议这样组织：

```
工作记录本/
├── core/                  # 共享资产（唯一源）
│   ├── schema.sql         # 建表 SQL —— 三端都读这一份
│   ├── schedule-cases.json# 排期算法的共享测试用例
│   └── src/schedule.rs    # Rust 排期实现（桌面/安卓直接引，鸿蒙做对齐）
├── ui/                    # 共享前端
│   ├── shared/            # app.js 的数据层与渲染逻辑
│   ├── desktop.css        # 现有 804 行（保留）
│   └── mobile.css         # 新增：移动布局（安卓 + 鸿蒙共用）
├── platforms/
│   ├── desktop/           # Tauri 桌面（现有 app/src-tauri 迁过来）
│   ├── android/           # Tauri Android（复用 desktop 的 Rust）
│   └── harmony/           # DevEco 工程（ArkTS）
└── docs/
```

⚠️ **鸿蒙工程必须放在英文路径下**。DevEco / hvigor 对中文路径会直接报 `Invalid project path` 构建失败。而当前项目根目录是 `C:\Users\Lenovo\Desktop\工作记录本\`——**中文**。

处理方式三选一：

1. 把项目根目录改成英文（如 `C:\Users\Lenovo\Desktop\WorkLuLu\`），中文只留在交付文件名上。**推荐**，一次到位。
2. 只把 `platforms/harmony/` 放到英文路径（如 `D:\dev\worklulu-harmony\`），用目录链接接回来。
3. 鸿蒙工程完全独立成一个仓库。

## 四、鸿蒙版的三条技术路线

### 4.1 路线甲：纯 ArkTS 原生（推荐方向）

用 ArkUI 声明式 UI 重写界面，数据用 `RelationalStore`。

- **优点**：真原生，流畅，符合鸿蒙设计规范，审核最稳
- **缺点**：3835 行前端 + 界面逻辑全部重写
- **适合**：想要长期做、要上架、要原生体验

### 4.2 路线乙：ArkTS 壳 + Web 组件（快速起步）

ArkTS 只做壳和原生能力（通知、卡片、文件），界面用 `Web({ src: $rawfile('index.html') })` 加载现有前端。

- **优点**：**3835 行前端直接复用**，安卓版和鸿蒙版可以共用同一份移动前端（改一处两端生效）
- **缺点**：需要写 JSBridge 双向通信层；性能不如原生；**有上架审核风险**（见 5.2）
- **适合**：想快速验证、或自用/小范围分发

⚠️ 几个已知的坑（社区实践反馈）：
- `rawfile` 目录名**必须全小写**，否则资源找不到
- 本地 HTML 里的 JS/CSS/图片**只能用相对路径**，不支持绝对路径
- 页面返回后 Web 组件会被销毁，**不保存 `WebviewController` 状态会白屏**
- 建议关掉 `zoomAccess`，否则双指缩放会把布局搞乱

### 4.3 路线丙：ArkTS + Rust（ohos-rs 复用排期算法）

ArkTS 做 UI，**排期算法通过 `ohos-rs` 复用现有 Rust 代码**——这是解决 2.3 那条纪律的最优解。

- **工具链**：`cargo install ohrs`，加 `napi-ohos` / `napi-derive-ohos` / `napi-build-ohos`，编译 target 是 `aarch64-linux-ohos`
- **写法**：`#[napi]` 宏把 Rust 函数导出成 ArkTS 可调用的接口
- **现状**：`ohos.rs` 是活跃的社区项目（非华为官方），已有实际案例（brotli 移植、HarmonyDesk 等）
- **取舍**：省下重写算法的成本 + 保证三端语义一致；代价是多一层 NAPI，构建链更复杂

**另一个选择**：直接用 ArkTS 重写 `schedule.rs`（约 500 行），然后用 `schedule-cases.json` 做三端对齐测试。**更简单，我倾向这个**，除非后面算法变得很复杂。

## 五、鸿蒙的两个现实约束（比技术更难）

### 5.1 分发：不能像 exe 那样"发个文件让用户自己装"

鸿蒙的签名体系是这样的：

| 签名类型 | 能否安装 | 能否上架 | 设备限制 |
|---|---|---|---|
| 未签名 | 不能 | 不行 | — |
| **Debug 签名** | **仅已注册 UDID 的设备** | 不行 | **最多 100 台**（官方限制） |
| **Release 签名** | 目标设备 | 可以 | 需在 AGC 申请证书 |

**关键点**：HarmonyOS NEXT 默认**不支持用户自由侧载**，应用主要通过应用市场分发。

对本项目这意味着：

- ❌ **不能像现在发 exe 一样，在吾爱破解发个 hap 让用户下载安装**
- ⚠️ 给朋友装，得把他的设备 UDID 加进 AGC 的调试设备列表（**上限 100 台**，用超了要删旧的）
- ✅ 正经做法是上架 AppGallery
- ⚠️ 上架要走：**实名认证 → AGC 创建应用 → 申请 Release 证书和 Profile → 本地签名 → 工信部 APP 备案（中国大陆必做）→ 提交审核**
- ⚠️ **个人开发者账号无法开通推送能力**（需要企业账号）—— 这对「到期提醒」是硬伤，但可以用本地通知绕过（本地通知不依赖推送通道）

**这一条必须先想清楚再动工。** 如果目标只是"我自己手机上能用"，那没问题（调试签名 + 自己的设备）；如果目标是"发给吾爱那批用户"，鸿蒙版的分发路径和 Windows 版完全不同，甚至可能走不通。

### 5.2 上架审核：纯 H5 套壳会被拒

华为应用市场审核指南 3.5 明确写着：

> 应用不得是**简单打包的网站页面**或套用模板、内容聚合、罗列链接、广告推广等

社区反馈也一致：单一封装 H5、无原生交互的应用通常过不了审，**需要至少集成一项鸿蒙原生能力**。

如果走路线乙（Web 组件），要想过审，得补上原生能力。对本项目来说，最自然的是：

- **服务卡片（桌面小组件）** —— 显示今天的待办，点一下进应用。这个和产品调性非常契合，而且**安卓那边也该做**（Android App Widget）
- 通知点击直达某条工作
- 一键直达 / 元服务

另外审核指南 3.7 提示「记事本、日历」等类别已经比较饱和，需要提供**独特价值**——本项目的差异点是"本地优先 + 模板 + 周期排期"，文案上要突出这点。

## 六、工具链与环境

### 6.1 两端都需要的

| 项 | 现状 | 说明 |
|---|---|---|
| Rust | ✅ 已装 | 安卓用 |
| JDK 17+ | ❌ 未装 | **两端都要**（安卓 Gradle / 鸿蒙 hvigor 都依赖 Java） |
| Node.js | ✅ 已装 | 鸿蒙 hvigor 是 Node DSL |

### 6.2 安卓侧（详见另一份文档）

Android Studio + SDK + NDK + `cargo-ndk` + 4 个 rust target + `tauri-cli`。

### 6.3 鸿蒙侧

| 项 | 说明 |
|---|---|
| DevEco Studio | 官方 IDE（IntelliJ fork），Windows 版可用；**只有稳定版，无 Canary** |
| HarmonyOS SDK | 目标 API Level **≥ 10**（NEXT 门槛） |
| Rust target | `rustup target add aarch64-linux-ohos`（如果走路线丙） |
| 华为开发者账号 | 需实名认证（个人约 1 个工作日） |
| 签名 | 调试可用 SDK 自动签名（**需联网**）；发布需在 AGC 申请 |
| hdc | 鸿蒙版的 adb，SDK 自带 |

⚠️ 已知体验问题：**hvigor 冷构建比同规模 Gradle 慢 2–4 倍**（社区普遍反馈）。

## 七、建议的推进顺序

**别两个版本同时开工。** 建议：

1. **先做安卓版**——技术路线已经清楚（Tauri 2 Android），复用率最高，分发没有障碍（apk 自由发），能最快看到成果。
2. **安卓版顺手把共享层拆出来**——`core/schema.sql`、`ui/mobile.css`、`schedule-cases.json`。这一步做完，鸿蒙版的成本会大幅下降。
3. **再评估鸿蒙版**——那时你对"移动端要什么"已经有了真实感受，再来决定鸿蒙走甲/乙/丙哪条路，以及**分发问题怎么解**。

先做安卓还有个隐秘好处：**移动端的触屏交互设计（前面那份文档里列的那 34 处 hover、拖拽、右键菜单）只需要设计一次**，鸿蒙版直接沿用同一套交互范式。

## 八、待确认前提

在动工之前，需要你明确的：

1. **鸿蒙目标设备是什么版本？** 纯血鸿蒙（HarmonyOS NEXT 5.0+）还是 HarmonyOS 4.x？
   （4.x 能装 apk，那"鸿蒙版"其实可以直接用安卓版；NEXT 才必须走 ArkTS 重写）
2. **鸿蒙版打算怎么分发？** 自己用 / 给朋友（100 台调试额度内）/ 正经上架 AppGallery？
   —— 这直接决定签名策略和要不要做原生功能凑审核要求。
3. **鸿蒙版 UI 走路线甲（纯 ArkTS）还是乙（Web 组件复用）？**
   —— 我的建议是先按乙快速出可用版，验证产品形态；确定要长期做再逐步甲化。
4. **项目根目录的中文路径要不要改？**（鸿蒙工程硬要求英文路径）
